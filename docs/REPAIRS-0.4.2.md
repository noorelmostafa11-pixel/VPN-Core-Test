# إصلاحات البروتوكولات الأربعة — 0.4.2

تنفيذ البنود R1–R9 المعتمدة، على مصدر 0.4.1-expanded. قاعدة المقارنة هي نتائج VLESS/Trojan/VMess/Shadowsocks السابقة، وليست نتيجة اختبار إنترنت جديد. ملفات الروابط الأصلية لا تُعاد كتابتها؛ ID يبقى SHA256 للرابط الأصلي بعد trim كما في النسخة السابقة. UUID وكلمات المرور والعناوين والمفاتيح ومسارات العقد لا تُستبدل بقيم مخمّنة.

| البند | ما كان ينقص | ما أضافه التنفيذ |
|---|---|---|
| R1 | JSON بصيغة form وحقول اختيارية فارغة وflow=none وطبقة plugin إضافية محددة | فك ترميز محصور في الحقل وبحسب مخططه؛ `%2B` يبقى plus حرفيًا، وبيانات الدخول لا تتأثر. plugin معروف مع طبقة إضافية واحدة فقط، بما فيها الترميز المختلط. الأصل محفوظ. |

تفسير R2 مهم: حذف كل عقدة تعرض h2 دون HTTP/1.1 مسبقًا كان يستبعد 8 عقد PASS سابقة. لذلك لا نضيف ALPN غائبًا، ولا نرسل HTTP/1.1 تحت h2 متفاوض عليه، ونحتفظ بالتوافق عندما يرفض السيرفر تفاوض ALPN أصلًا. الحقول الجديدة `alpn_compatibility` و`alpn_configuration_reason_code` توضح ذلك قبل الاختبار. هذا لا يدّعي تنفيذ WebSocket عبر HTTP/2 أو HTTP/3.

التعامل مع plugin يحافظ على دلالات parser السابق: حقول plugin غير المطبقة سابقًا، مثل sni الوصفي، لا تُحوّل إلى SNI جديد. skip-cert-verify داخل plugin يُسجّل كطلب قديم، ولا يعطل التحقق. JSON المبتور ومفاتيح REALITY/SS2022 الناقصة لا تُصلح بتخمين.

في HTTP/3 يُحفظ السبب الرقمي الآمن من خطأ TLS ذي النوع المعروف قبل عبوره طبقة QUIC التي قد تفقد هذا النوع. الحفظ يخص محاولة اتصال واحدة فقط، ولا يستنتج سبب الشهادة من نص الرسالة. فشل طلب HTTP بعد مصافحة ناجحة لا يُصنّف مهلة TLS بلا دليل.

الحصر على الملفات الأربعة الأصلية: 72,767 مدخلًا، منها 71,748 كونفيج مقبولًا و1,019 مرفوضًا بسبب بيانات ناقصة/غير صالحة/غامضة. استعاد R1 قراءة 113 مدخلًا؛ وفحص HTTP المبكر رفض 15 إضافية قبل الشبكة. كل 1,637 PASS السابقة بقيت مقبولة في الحصر. هذا لا يضيف PASS شبكية جديدة، ولا يصحح القيم المفقودة باختراعها.

الحصر وإثبات ثبات الملفات وIDs في `repair-inventory-0.4.2.json`. الدليل التنفيذي وأرقام الاختبارات وبصمات الملفات في `repair-validation-0.4.2.json`. نجاح الحصر لا يعني نجاح اتصال؛ يبقى شرط PASS في الدفعات: curl exit=0، تحقق HTTPS، HTTP 200، جسم غير فارغ، ومطابقة SHA256 إذا حدده المستخدم.

اختبار Vision السابق كان يستخدم نفس كائن SSL من خيطين متزامنين، وهو استخدام غير مدعوم. أُعيد الفشل على 0.4.1 أيضًا، وصُحح عميل الاختبار فقط إلى مالك واحد، مع الإبقاء على نقل 350,007 bytes والتحقق من hash وانتقال direct عبر padding مجزأ. 12 إعادة متتالية نجحت بعد التصحيح. المرجع: [OpenSSL thread safety](https://docs.openssl.org/master/man7/openssl-threads/).

ظهر الاستخدام نفسه في عميل اختبار XTLS القديم؛ صُحح إلى مالك SSL واحد مع الاحتفاظ بنقل 300,019 bytes ومقارنة SHA256 وبجميع حالات البروتوكول والبصمة والانتقال. هذه تغييرات في أدوات الاختبار، وليست تغييرًا في تشفير الكور أو صيغة العقدة.

مرجع السلوك: [RFC9110 §5.2–5.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.3)، [Winsock select](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select)، [curl error codes](https://curl.se/libcurl/c/libcurl-errors.html).

Windows amd64 مبني ببصمات وimports/exports متحقق منها. الاختبار التنفيذي هنا على Linux/PowerShell 7؛ التشغيل على Windows الحقيقي وWindows PowerShell 5.1 يحتاج تجربة اللاب. المثبت يأخذ backup ويعمل rollback عند الخطأ ويحافظ على defaults المحلية للمهلة والرابط والتوازي وcurl وbody hash.
